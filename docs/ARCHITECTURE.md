# 生产架构说明

本文档说明演示骨架如何演进为支撑上百项控制、多审核周期、可向认证审核员举证的生产平台。
核心域逻辑（`lib/isms`）保持纯 Ruby、零外部依赖、可独立测试；Rails/PG/Sidekiq 只是
外围的持久化、调度与管理界面层，不参与符合性判定——判定逻辑永远可以离线重算、复核。

## 1. 分层架构

```
┌──────────────────────────────────────────────────────────────────┐
│ Rails 管理界面：规则维护、例外审批工作流、身份裁决队列、证据包下载   │
├──────────────────────────────────────────────────────────────────┤
│ Sidekiq 定时采集（按源分级调度）  │  重算 Worker（规则/映射变更触发） │
├──────────────────────────────────────────────────────────────────┤
│ 连接器层    HR / 代码仓库 / 云IAM / 补丁 / 工单（各带重试与限流）     │
│   ├─ RawRecord 原样落库（追加写，不可更新删除，留存期 ≥ 2 审核周期）  │
│   └─ 规范化模型（术语/字段/时间格式统一，例如 blocked→disabled）      │
├──────────────────────────────────────────────────────────────────┤
│ 身份映射层  确定性映射表 + 置信度阈值 + 人工裁决（绝不模糊猜测）       │
├──────────────────────────────────────────────────────────────────┤
│ 规则引擎    声明式 YAML 规则（带版本）+ 处理器库 + 双时态区间求值      │
├──────────────────────────────────────────────────────────────────┤
│ 证据层      时间轴结论 + 原始数据引用 + 例外记录 + SHA-256 封存清单   │
├──────────────────────────────────────────────────────────────────┤
│ PostgreSQL（tstzrange/GiST）  对象存储（证据包归档，WORM/对象锁）     │
└──────────────────────────────────────────────────────────────────┘
```

## 2. 三个核心难点的生产级解法

### 2.1 数据口径对不上

| 差异类型 | 处理位置 | 手段 |
| --- | --- | --- |
| 术语差异（blocked/disabled/suspended） | 连接器规范化层 | 枚举映射表，引擎只接触规范值；新术语出现时连接器测试失败而不是静默漏报 |
| 标识差异（工号/用户名/ARN/邮箱） | 身份映射层 | 显式映射 + 置信度；低置信度与无映射进裁决队列，由 GOV-01 控制兜底报告 |
| 时间口径（时区、粒度、业务时间 vs 采集时间） | RawRecord 双时态字段 | `observed_at`（事实生效）与 `collected_at`（拉取时间）分开存储 |
| SLA/逾期字段各系统算法不同 | 规则参数统一计算 | 如补丁截止时间一律由发布时间 + 规则声明的 SLA 推导，不采信源系统自报值 |

映射表本身受版本管理：每次映射变更记录变更人、时间与依据，证据包附带当时生效的映射版本。

### 2.2 合理例外

- 例外是**带审批链的有效期对象**，不是结论上的备注。引擎在时间轴上做区间交叠，
  豁免只在"控制 + 资源 + 时间"三维匹配且例外自身合法（已审批、SoD、未过期、有理由）时生效。
- 例外到期不需要人工关闭：下次求值自动恢复违规判定（演示中 wangwu 账号即如此）。
- 非法例外（自审批、缺审批）在加载阶段被拦截并记录，绝不进入求值上下文。
- 每条例外强制登记补偿控制，审核员据此评估残余风险；管理界面对临期例外（如 14 天内到期）
  自动提醒责任人续签或整改。
- Rails 层的例外审批流与工单系统双向校验：工单状态被撤销时，对应例外同步失效并重算历史区间。

### 2.3 证明整个周期有效（而非某个时点）

- **事件流而非快照**：账号、补丁等全部保存状态变更流水，引擎可重建任意历史时刻的状态。
- **区间求值**：审核周期被切分为 `effective / violated / exempted / gap` 四类半开区间，
  分段拼接恰好覆盖完整周期；结论不是"检查当天合规"，而是"周期内每一小时处于什么状态"。
- **数据缺口即发现**：采集失败或间隔超期产生 gap 段。一个"零违规"结论若伴随大段 gap，
  汇总状态只会是 `gap` 而不是 `effective`，无法用停采来粉饰。
- **双时态与可重算**：RawRecord 追加写、不可改；规则带版本。任何历史周期都可以用
  当时的规则版本 + 当时的数据快照**确定性重放**，重放结果与封存证据包哈希一致。
- **证据封存**：证据包写入对象存储后开启 WORM/对象锁，保留期覆盖认证要求；
  `sha256_manifest.txt` 使审核员能验证包内任何文件未被篡改。

## 3. PostgreSQL 存储设计要点

```sql
-- 原始记录：追加写
CREATE TABLE raw_records (
  raw_id        text PRIMARY KEY,
  source        text NOT NULL,
  entity_type   text NOT NULL,
  payload       jsonb NOT NULL,
  observed_at   timestamptz NOT NULL,
  collected_at  timestamptz NOT NULL
);

-- 身份映射：带版本与生效区间（双时态）
CREATE TABLE identity_mappings (
  id bigserial, person_id text NOT NULL, source_system text NOT NULL,
  external_login text NOT NULL, confidence numeric(3,2) NOT NULL,
  valid_range tstzrange NOT NULL, EXCLUDE USING gist (
    source_system WITH =, external_login WITH =, valid_range WITH &&
  ) WHERE (confidence >= 0.8)
);

-- 评估结论分段：GiST 支持"某时刻哪些控制处于违规"这类时间轴查询
CREATE TABLE control_segments (
  control_id text NOT NULL, status text NOT NULL,
  segment_range tstzrange NOT NULL, evidence jsonb NOT NULL,
  rule_version text NOT NULL,
  EXCLUDE USING gist (control_id WITH =, segment_range WITH &&)
);
```

## 4. 从上百项控制扩展的方式

新增一项控制 = 一个 YAML 规则文件 + 一个处理器方法（或复用现有处理器，仅改参数）：

1. 在 `config/controls/` 声明控制：标准条款、SLA 参数、依赖数据源、证据负责人、版本号。
2. 在 `Evaluator::HANDLERS` 登记处理器。多数控制可归为三类既有模式：
   **时限类**（事件 A 后 N 小时内必须发生事件 B，如离职禁用、补丁）、
   **门禁类**（动作发生前必须满足条件，如评审、变更审批）、
   **清点类**（资产/账号/配置的存在性与覆盖率，如身份映射、资产登记）。
3. 处理器只输出分段与发现，不做展示与持久化，保证单元测试无需数据库。
4. 规则版本升级走 Pull Request + 评审；合并后重算 Worker 自动重算受影响周期，
   历史已封存证据包不变，新版本只影响此后的评估。

## 5. 运营闭环

- 管理界面四个工作队列：**违规整改**、**例外审批/续签**、**身份裁决**、**采集故障**。
- 每条发现可指派责任人、关联整改工单；工单关闭后自动重评对应区间。
- 月度生成"控制健康度"趋势（各控制周期内有效时长占比），把年度审核变成日常度量。
- 证据包生成支持按审核员要求裁剪控制范围，但裁剪动作本身写入 manifest，防止选择性举证。
